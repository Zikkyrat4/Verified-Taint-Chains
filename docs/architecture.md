# Архитектура

VTC реализует 4-этапный пайплайн анализа безопасности Java-кода.

```
Java-файл
  |
  v
Этап 1: LLM-инференс
  |  Извлечение sources и sinks через LLM
  v
Этап 2: Поиск путей
  |  Построение графа потоков данных, поиск путей A*/BFS
  v
Этап 3: Верификация
  |  CFG-анализ и/или символьное выполнение (Z3)
  v
Этап 4: Объяснение
  |  Генерация описаний уязвимостей, рекомендаций, CWE
  v
Результат: JSON с верифицированными уязвимостями
```

## Этап 1 — LLM-инференс

**Модуль:** `src/stage1_llm_inference/`

Анализирует Java-код и определяет:
- **Sources** — точки входа небезопасных данных (пользовательский ввод, файлы, HTTP-параметры)
- **Sinks** — опасные операции (SQL-запросы, системные команды, вывод в HTML)

### Процесс работы

1. **AST-парсер** (`ast_parser.py`) извлекает методы из Java-файла. Использует tree-sitter, при его недоступности — fallback на regex с подсчётом фигурных скобок.

2. **Specification Extractor** (`specification_extractor.py`) для каждого метода:
   - Извлекает контекст (импорты, иерархия классов, сигнатуры методов)
   - Формирует промпты с контекстом через шаблоны из `prompt_templates.py`
   - Отправляет промпт в LLM через `chat_with_json_prompt()`
   - Парсит JSON-ответ в объекты `Source` и `Sink`

По умолчанию используется `ANALYSIS_BACKEND=llm`: только ответы модели могут
создать `Source`/`Sink`. AST применяется для структурирования кода и
последующей проверки, но не подменяет результат модели. Статические endpoint-
правила доступны как отдельный backend `static`; их явное объединение с LLM
возможно только в режиме `hybrid`.

3. **LLM-клиенты** (`openai_client.py`, `ollama_client.py`) — реализации для OpenAI API и Ollama. Ollama-клиент использует `format="json"` для гарантированного получения JSON.

### Результат

Объект `Specification` со списками `sources`, `sinks` и `sanitizers`.

## Этап 2 — Поиск путей

**Модуль:** `src/stage2_path_discovery/`

Строит граф потоков данных и ищет пути от sources к sinks.

### Построение графа

**EnhancedGraphBuilder** (`graph_builder.py`) анализирует код и строит граф NetworkX:
- Узлы: переменные с метаданными (строка, тип, имя функции)
- Рёбра: потоки данных (присваивания, вызовы методов, возвраты)
- Отслеживает типы переменных и связи через вызовы методов

**Joern** (`joern_wrapper.py`) — опциональная интеграция. Если Joern установлен и `USE_JOERN=true`, используется для построения Program Dependence Graph (PDG). При недоступности — автоматический fallback на EnhancedGraphBuilder.

### Алгоритмы поиска

- **A*** (`astar_search.py`) — поиск с семантической эвристикой на основе CodeBERT-эмбеддингов. Оценивает семантическую близость промежуточных узлов к целевому sink. Исследует на 30-50% меньше узлов по сравнению с BFS.
- **BFS** (`bfs_pathfinder.py`) — поиск в ширину. Гарантирует нахождение кратчайшего пути. Проще, но медленнее на больших графах.

### Результат

Список объектов `TaintChain` — цепочек от source к sink через промежуточные узлы.

## Этап 3 — Верификация

**Модуль:** `src/stage3_verification/`

Проверяет найденные цепочки на реальную достижимость.

### Уровни верификации

Настраивается через `VERIFICATION_LEVEL`:

- **`cfg`** — анализ графа потока управления (Control Flow Graph). Быстрая проверка достижимости: существует ли путь выполнения, в котором данные проходят от source к sink. Учитывает условные ветвления и циклы.

- **`symbolic`** — символьное выполнение через Z3 SMT-солвер. Моделирует переменные как символьные значения, собирает ограничения по пути выполнения, проверяет выполнимость (SAT). Более точный, но медленный метод.

- **`both`** — сначала CFG (быстрый фильтр), затем символьное выполнение для прошедших CFG-проверку. Оптимальное соотношение точности и скорости.

### Результат

Каждой цепочке присваивается статус:
- `verified` — путь подтверждён
- `false` — путь невозможен
- `unverifiable` — недостаточно информации для вывода

## Этап 4 — Объяснение

**Модуль:** `src/stage4_explanation/`

Генерирует описания верифицированных уязвимостей.

### Шаблоны уязвимостей

Для каждого типа (SQL Injection, XSS, Command Injection, Path Traversal, XXE, SSRF) содержит:
- Описание проблемы и механизма эксплуатации
- Стратегии исправления (2–5 вариантов с приоритизацией)
- Примеры безопасного кода
- Ссылки на CWE и OWASP

### Генерация объяснений

**ExplanationGenerator** (`explanation_generator.py`) для каждой цепочки:
1. Выбирает шаблон по типу уязвимости
2. LLM генерирует контекстное описание (почему уязвимо, как исправить, пример исправления)
3. Рассчитывает уверенность: 40% LLM + 50% верификация + 10% длина пути
4. Определяет severity (LOW/MEDIUM/HIGH/CRITICAL) с поправками на уверенность и наличие санитизаторов

### Результат

Объекты `Explanation` с полями: `why_vulnerable`, `how_to_fix`, `example_fix`, `severity`, `cwe_id`.

## Оркестратор

**Модуль:** `src/pipeline/orchestrator.py`

`SimplePipeline` координирует выполнение этапов:

1. Читает Java-файл
2. Создаёт LLM-клиент (OpenAI или Ollama) по конфигурации
3. Запускает Этап 1 → получает `Specification`
4. Запускает Этап 2 → получает список `TaintChain`
5. Запускает Этап 3 → фильтрует по `verified` статусу
6. Запускает Этап 4 → генерирует `Explanation` для каждой цепочки
7. Возвращает результат с метриками

## CLI и benchmark

**CLI:** `src/pipeline/main.py`

Единая команда `vtc` предоставляет отдельные подкоманды:

- `vtc analyze` запускает production-анализ Java-файла или проекта;
- `vtc sinks` собирает инвентарь опасных sinks;
- `vtc evaluate` запускает benchmark по размеченным фикстурам.

Строгий matcher, runner и генерация benchmark-отчётов находятся в
`src/evaluation/engine.py`. Ground truth читается только этим модулем после
завершения pipeline и не передаётся Stage 1-4.

## Модели данных

**Модуль:** `src/core/models.py`

| Модель | Описание |
|--------|----------|
| `Source` | Источник небезопасных данных (переменная, строка, тип, уверенность) |
| `Sink` | Опасная операция (переменная, строка, тип уязвимости, уверенность) |
| `PathNode` | Узел пути (source / intermediate / sink) |
| `TaintChain` | Цепочка source → [промежуточные узлы] → sink |
| `Specification` | Результат Этапа 1 (списки sources, sinks, sanitizers) |
| `Explanation` | Объяснение уязвимости (описание, исправление, severity, CWE) |
| `VulnerabilityType` | Enum: sql_injection, xss, command_injection, path_traversal, xxe, ssrf |
| `VerificationStatus` | Enum: verified, false, unverifiable |
